# AI Company 운영 모델

> **상태**: 제안 **목적**: `ehowlsla`가 상정하는 역할/책임/오너 개입 원칙을 범용 operating model로 정리한다. **대상 독자**: 회사 구조와 역할 책임 모델을 설계하려는 독자 **관련 문서**: `README.md`, `CONCEPT-MAP.md`, `ORCHESTRATION-PATTERNS.md`**정합 기준**: `../PRODUCT.md`, `../SPEC-implementation.md`

이 문서는 `ehowlsla` 브랜치에서 상정하는 **범용 AI 회사 운영 모델**을 정리한다. 특정 프로젝트 사례는 `examples/` 아래 문서를 참고하고, 여기서는 어떤 프로젝트에도 적용 가능한 역할/책임/오너 개입 원칙을 다룬다.

이 문서의 `오너`는 기준 권한 주체 `board`를 solo-operator UX로 다시 부르는 표현이다. 즉 권한 체계를 바꾸는 문서가 아니라, **기본 운영 인터페이스를 어떻게 보이게 할지**를 설명하는 overlay 문서다.

## 1. 비전

Paperclip이 지향하는 것은 “agent를 많이 띄우는 시스템”이 아니라, **사람 조직처럼 역할과 책임을 가진 AI 회사**다.

핵심 전환은 이것이다.

- 기존: 스크립트와 사람이 흐름을 나눠서 관리한다.
- 목표: 에이전트가 판단과 위임을 맡고, 스크립트/도구는 실행기로 남으며, 오너는 CEO를 통해 회사를 다룬다.

## 2. 오너 커뮤니케이션 원칙

오너(보드)는 기본적으로 **CEO와만 커뮤니케이션하는 것**을 원칙으로 둔다.

즉 기본 운영 구조는:

- 오너 ↔ CEO
- CEO ↔ 실무 역할

이다.

오너는 주로 아래만 본다.

- 지금 무엇을 밀고 있는가
- 중간 산출물이 어떤가
- 최종 결과물이 만족스러운가
- 비용/리스크/막힘이 있는가

오너가 마음에 들지 않을 때도, 실무자별 세부 교정자가 되기보다 **CEO에게 강한 피드백을 주고 방향을 다시 맞추는 구조**가 기본이다.

## 3. 최소 조직 원칙

모든 회사를 처음부터 크게 만들 필요는 없다. 초기에는 아래 네 종류의 역할만 있어도 충분하다.

1. **CEO**
   - 방향 설정, 우선순위, 오너 커뮤니케이션, 최종 패키지 보고
2. **Domain Lead**
   - 도메인 핵심 판단 담당 (예: 스토리, 콘텐츠, 분석, 기획)
3. **Production / Execution Lead**
   - 도구 실행, 자동화, 안정성, 배포, 복구 담당
4. **QA / Review 역할**
   - 필요할 때만 추가되는 품질 검토 담당

즉, 구체적 역할명은 프로젝트마다 달라도, 대부분 회사는 이 네 축으로 설명할 수 있다.

## 4. 역할 책임을 나누는 기본법

### CEO

- 회사 목표를 해석한다.
- 어떤 결과물을 오너에게 올릴지 결정한다.
- 내부 역할에 일을 분해하고 handoff를 관리한다.
- review / approval가 필요한지 판단한다.

### Domain Lead

- 도메인 특화 판단을 담당한다.
- 입력을 usable package로 정리한다.
- 무엇이 중요한지, 무엇이 빠졌는지 판단한다.

### Production / Execution Lead

- deterministic 도구와 파이프라인을 다룬다.
- 실행 안정성, 복구, 배포, 반복 작업을 맡는다.

### QA / Review 역할

- 품질 기준이 필요한 경우에만 활성화한다.
- 결과물이 충분히 좋은지 판단한다.
- 승인권자와는 구분한다.

## 5. 품질 검토(review)와 승인(approval)

이 둘은 반드시 구분한다.

- **품질 검토(review)**: 결과물이 충분히 좋은가?
- **승인(approval)**: 이 행동을 허용할 것인가?

### 오너 개입 원칙

- 품질 검토와 승인은 **항상 오너가 직접 해야 하는 단계가 아니다.**
- 기본 운영에서는 CEO나 내부 역할이 review를 소화한다.
- 오너는 **최종 산출물 확인 / 방향 재조정 / 고위험 승인**에만 개입하는 편이 효율적이다.
- 즉 review와 approval은 `강제 workflow`라기보다 `필요할 때 켜는 통제 장치`로 보는 편이 맞다.

## 6. 회사가 다루는 기본 단위

범용적으로 Paperclip 회사는 아래 단위를 다룬다.

- 회사
- 역할(에이전트)
- 프로젝트
- issue
- 문서(documents)
- work-products
- 운영 루틴(routines)
- runs
- review / approval

중요한 점은, 오너가 직접 보는 단위는 이 primitive 자체가 아니라 **결과물 묶음(deliverable bundle)** 이어야 한다는 것이다.

## 7. 프로젝트와 에이전트의 관계

기본적으로는 **같은 회사의 에이전트가 여러 프로젝트를 맡는 구조**를 상정한다.

즉:

- 회사 = 에이전트 조직
- 프로젝트 = 그 조직이 수행하는 개별 업무 단위
- issue = 프로젝트 안의 실제 작업

이 모델에서는 프로젝트마다 완전히 다른 회사를 만드는 것이 아니라, 같은 CEO / Domain Lead / Production Lead가 여러 프로젝트를 오가며 일할 수 있다.

물론 실무적으로는 프로젝트별로 참여 멤버가 달라질 수 있다.

예:

- 프로젝트 A는 Story Lead + Casting Lead 중심
- 프로젝트 B는 Platform Engineer + QA 중심

즉 **에이전트는 회사 공용이지만, 프로젝트마다 실제 참여 구성은 달라질 수 있다.**

## 8. 회사 공용 기억 / 프로젝트 전용 기억 / 에이전트 개인 지식

하나의 회사가 여러 프로젝트를 유기적으로 수행하려면, 지식을 아래처럼 **세 층**으로 나눠 생각하는 것이 좋다.

### 1) 회사 공용 기억

- CEO 운영 원칙
- 품질 기준
- 결과물 묶음(deliverable bundle) 규약
- 반복 운영 routine
- 잘 먹힌 review checklist
- 재사용 가능한 playbook

이 층은 프로젝트 A에서 검증된 좋은 방식을 프로젝트 B로 옮기는 데 쓰인다.

### 2) 프로젝트 전용 기억

- 작품/제품의 목표
- 특정 리포지토리, 자산, 런타임 설정
- 해당 프로젝트에서만 통하는 도메인 판단
- 특정 이슈/패킷의 상태와 맥락

이 층은 개별 프로젝트의 고유성을 보존한다.

### 3) 에이전트 개인 지식

- 특정 역할이 잘 쓰는 작업 습관
- 자주 참고하는 체크 순서
- 개인용 프롬프트/작업 요령
- 특정 도구를 다루는 숙련도

이 층은 개인 생산성을 높여주지만, 회사의 표준은 아니다. 좋은 방식이 반복적으로 검증되면 CEO나 리드가 이를 회사 공용 기억으로 올릴 수 있다.

## 8.1 승격 규칙

핵심은: **A의 노하우를 B에 재사용하려면, CEO가 A의 성공 방식을 회사 공용 기억으로 승격해야 한다**는 것이다.

자동으로 집단지성이 생기는 모델보다는, 좋은 운영 방식을 회사 표준으로 올리는 모델에 가깝다.

간단히 말하면:

```text
에이전트 개인 지식 → (반복 검증) → 프로젝트 전용 방식 → (CEO 정리) → 회사 공용 기억
```

### 무엇을 어디에 둘까

| 층 | 담는 것 | 다른 프로젝트에 자동 적용? | 누가 관리하나 |
| --- | --- | --- | --- |
| 회사 공용 기억 | 회사 표준, 패키지 규약, checklist, routine, playbook | 예 | CEO / 리드 |
| 프로젝트 전용 기억 | 작품 목표, repo/workspace, 프로젝트별 판단, packet 상태 | 아니오 | 프로젝트 리드 |
| 에이전트 개인 지식 | 개인 작업 습관, 숙련도, 개인 메모 | 아니오 | 각 에이전트 |

### 주의점

- 개인 지식을 곧바로 회사 표준처럼 취급하면 혼란이 커진다.
- 프로젝트 전용 판단을 무리하게 공용 규칙으로 올리면 개별 프로젝트 품질이 떨어질 수 있다.
- 회사 공용 기억은 적어도 **다음 프로젝트에서도 다시 쓰고 싶은 것**만 남기는 편이 좋다.

## 9. 언제 역할을 늘려야 하나

역할을 늘리는 기준은 “멋져 보이기”가 아니라 아래다.

- CEO가 직접 다 조율하기 어려울 때
- 특정 도메인 판단이 분명히 분리될 때
- production과 판단이 서로 병목을 만들 때
- 오너가 더 이상 같은 문제를 반복해서 피드백할 때

반대로 아래면 아직 과하다.

- 단순히 agent 수를 늘리고 싶을 때
- deterministic 도구를 agent로 바꾸기만 할 때
- 실제 handoff 없이 이름만 그럴듯하게 붙일 때
