# 기억 구조와 제품 표면

> **상태**: 제안
> **목적**: 회사 공용 플레이북 / 프로젝트 브리프 / 에이전트 작업 방식이 제품 어디에 드러나야 하는지 제안한다.
> **대상 독자**: 기억 표면과 플레이북 승격 흐름을 설계하려는 독자
> **관련 문서**: [`README.md`](./README.md), [`CONCEPT-MAP.md`](./CONCEPT-MAP.md), [`AI-COMPANY.md`](./AI-COMPANY.md), [`ORCHESTRATION-PATTERNS.md`](./ORCHESTRATION-PATTERNS.md)
> **정합 기준**: [`../PRODUCT.md`](../PRODUCT.md), [`../SPEC-implementation.md`](../SPEC-implementation.md)


이 문서는 `ehowlsla` 브랜치에서 정리한
**회사 공용 기억 / 프로젝트 전용 기억 / 에이전트 개인 지식**
3층 구조를 Paperclip 제품 안에서 어떻게 드러내야 하는지 정리한다.

이 문서의 내용은 대부분 **현재 기본 UI가 아니라 제안하는 제품 표면**이다.

핵심 목적은 하나다.

> 멀티 프로젝트 회사가 유기적으로 움직이되,
> 오너를 피곤하게 만들지 않고,
> 좋은 운영 방식을 다음 프로젝트로 재사용 가능하게 만든다.

## 1. 이 문서의 역할

- [`AI-COMPANY.md`](./AI-COMPANY.md)는 3층 기억 구조 자체를 정의한다.
- [`ORCHESTRATION-PATTERNS.md`](./ORCHESTRATION-PATTERNS.md)는 그 기억이 어떻게 승격되는지 설명한다.
- 이 문서는 그 구조를 **제품 화면과 편집 지점**으로 번역한다.

즉 이 문서는 “무엇을 기억해야 하는가?”보다
**“그 기억을 제품 어디에서 보고, 수정하고, 승격할 것인가?”**를 다룬다.

## 2. 기본 원칙

### 1) knowledge base처럼 크게 만들지 않는다

Paperclip은 일반 지식관리 툴이 아니라 control plane이다.
따라서 메모리를 무한히 쌓는 위키보다,
운영에 실제로 재사용되는 규칙과 패키지 기준만 잘 드러내는 편이 맞다.

### 2) 오너는 CEO 요약만 보면 된다

오너가 3층 기억 구조 전체를 직접 관리하면 다시 피곤해진다.
오너는 기본적으로:
- CEO 브리핑
- 대표 결과물 묶음(deliverable bundle)
- 정말 필요한 승인/판단

만 보면 된다.

### 3) 승격은 명시적으로 일어나야 한다

좋은 개인 습관이 자동으로 회사 표준이 되는 모델은 아니다.
반복 검증된 내용을 CEO나 리드가
회사 공용 기억으로 **승격**하는 흐름이 필요하다.

## 3. 3층 기억 구조를 어디에 둘까

| 층 | 제품에서 보여야 하는 곳 | 기본 편집 주체 | 기본 소비 주체 |
| --- | --- | --- | --- |
| 회사 공용 기억 | 회사 공용 플레이북 / 실행 패킷 규약 / 반복 운영 라이브러리 / review checklist | CEO / 리드 | 회사 전체 |
| 프로젝트 전용 기억 | 프로젝트 브리프 / 작업공간 설정 / 실행 패킷 목록 / 프로젝트 결정 기록 | 프로젝트 리드 | 해당 프로젝트 참여자 |
| 에이전트 개인 지식 | agent instructions / role habits / 개인 작업 메모 | 각 에이전트 | 해당 에이전트, 상위 리드 일부 |

## 4. 최소 제품 표면 제안

과한 지식 플랫폼을 만들지 않고도,
아래 네 군데만 잘 보여주면 3층 구조가 꽤 자연스럽게 작동할 수 있다.

### A. Company Playbook 표면

회사 공용 기억을 두는 대표 표면이다.

포함할 것:
- 회사 운영 원칙
- 결과물 묶음 규약
- review checklist
- publish / release 기준
- reusable routine 패턴
- 여러 프로젝트에서 재사용할 실행 패킷 템플릿

이 표면은 “회사 표준”을 담는다.
프로젝트별 특수사항을 여기에 과하게 넣으면 안 된다.

#### 최소 UX
- 회사 상세에서 `Playbook` 또는 `Operating Rules` 섹션
- CEO가 수정 가능
- 프로젝트에서 참조 링크 가능

### B. Project Brief / Packet 표면

프로젝트 전용 기억을 두는 대표 표면이다.

포함할 것:
- 프로젝트 목표
- 범위
- 저장소 / 작업공간 / 실행 환경 설정
- 해당 프로젝트에서만 쓰는 판단 기준
- 대표 실행 패킷 목록
- 현재 진행 중인 실행 패킷 상태

이 표면은 “이 프로젝트만의 맥락”을 담는다.

#### 최소 UX
- Project detail 상단에 `Brief`
- Project detail 안에 `Packets`
- 회사 playbook과 연결된 “기본 규약 상속” 표시

### C. Agent Working Style 표면

에이전트 개인 지식을 다루는 표면이다.

포함할 것:
- role-specific instructions
- 개인 작업 습관
- 도구 숙련 팁
- 자주 쓰는 체크 순서

이 표면은 “개인 생산성”을 위한 것이지,
곧바로 회사 표준은 아니다.

#### 최소 UX
- 기존 agent instructions bundle을 중심 표면으로 활용
- 필요하면 `personal notes` 또는 `working style` 필드 추가
- “회사 표준으로 승격 제안” 액션이 있으면 좋음

### D. 승격 흐름

이게 가장 중요하다.

개인 지식이나 프로젝트 전용 방식을
회사 공용 기억으로 올리는 흐름이 없으면,
멀티 프로젝트 회사는 유기적으로 학습하지 못한다.

#### 최소 UX
- 실행 패킷 review 또는 retrospective에서
  - `playbook으로 승격`
  - `검토 체크리스트로 저장`
  - `실행 패킷 템플릿으로 저장`
같은 액션을 제공

#### 흐름
```text
agent notes / project decision
  → CEO 또는 리드 검토
    → 회사 공용 플레이북 항목으로 승격
      → 다음 프로젝트에 재사용
```

## 5. 오너 화면에는 무엇이 보여야 하나

오너는 3층 기억 구조를 전부 탐색할 필요가 없다.

오너 화면에서 보여야 할 것은:
- CEO 브리핑 요약
- 현재 중요한 결과물 묶음
- 공용 플레이북이 바뀌었을 때 핵심 변화 요약
- 오너 판단이 필요한 변화만

즉 오너는
**기억 구조의 관리자**가 아니라
**결정자**로 남는 편이 맞다.

## 6. ai-jobdori에 대입하면

### 회사 공용 기억
- draft_package 형식
- publish 판단 기준
- retry / recovery 규칙
- 주간/월간 검토 방식

### 프로젝트 전용 기억
- `Daily Operations`의 현재 운영 상태
- `Content Improvement`의 실험 항목
- 외부 API / queue / 배포 경로

### 에이전트 개인 지식
- 큐레이터가 자주 쓰는 curation 체크 순서
- 작가가 초안 다듬을 때 쓰는 습관
- 엔지니어가 실패 복구할 때 보는 체크 포인트

여기서 잘된 방식이 반복적으로 검증되면,
편집장(CEO)이 회사 공용 checklist로 올리는 식이 자연스럽다.

## 7. rovel.ai2에 대입하면

### 회사 공용 기억
- adaptation brief 형식
- casting_package 기준
- release candidate 기준
- editor-pick 승격 기준

### 프로젝트 전용 기억
- 작품 A의 tone / 방향성
- 작품 B의 자산 제약
- 특정 프로젝트 저장소/작업공간/실행 환경
- 특정 작품 실행 패킷 상태

### 에이전트 개인 지식
- Story Lead의 정리 방식
- Casting Lead의 후보 정리 습관
- QA Lead의 점검 순서

여기서 중요한 것은,
모든 작품을 같은 방식으로 몰아붙이지 않고
작품별 특수성과 회사 공용 기준을 분리하는 것이다.

## 8. 제품에 바로 필요한 최소 기능

과하지 않게 시작하려면 아래 정도가 적당하다.

### P0에 가까운 것
1. 회사 공용 플레이북 표면
2. 프로젝트 브리프 + 실행 패킷 연결
3. 실행 패킷에서 플레이북 승격 액션

### P1에 가까운 것
4. 에이전트 작업 방식 / 개인 메모 표면
5. 플레이북 변경 diff / 요약
6. project가 어떤 회사 표준을 상속받는지 보여주는 표시

## 9. 하지 말아야 할 것

- 범용 위키처럼 문서를 무한히 늘리기
- 개인 메모를 바로 회사 표준처럼 취급하기
- 프로젝트 전용 특수사항을 공용 규칙에 과도하게 섞기
- 오너에게 이 모든 구조를 직접 관리하게 만들기

## 10. 한 줄 결론

Paperclip의 멀티 프로젝트 학습은
“자동 집단지성”보다
**개인/프로젝트의 좋은 방식을 CEO가 회사 표준으로 승격시키는 구조**
로 설계하는 편이 맞다.
